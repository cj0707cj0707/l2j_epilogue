# 51. Восстановление Cardinal/Bishop и ник противника при прибытии на Олимпиаду

База: `d70815d3b5cd31a09c5cd15468752376e9e890d3` (обязательный серверный Victory из50). Дополняет46, не отменяет фиксированные имена из45/46 и последующие боевые правила47–50.

## Cardinal: подтверждённые пробелы в коде

Живой GameServer, production DB и свежие логи недоступны. Изменения закрывают обнаруженные сценарии, но конкретная причина отсутствия бота на работающем сервере без логов не установлена.

- Положительный старый `BotCount=18` либо уже заполненный пул с повторным классом оставляли отсутствующий97 за пределами лимита. Теперь `spawnAll` сначала обеспечивает покрытие всех19 пресетов. Целевое количество — максимум настроенного лимита и суммы активных ботов с отсутствующими классами. Старые18 превращаются в19;19 ботов с дублем и без97 — в20. Уже существующие персонажи не удаляются. `Enabled=false` и `BotCount<=0` по-прежнему запрещают автоматическое заполнение. При ошибке восстановления класса произвольные дубли не маскируют пробел; остаётся `roster incomplete`.
- Исправление сохранения registry из46 предотвращает новые потери, но не возвращает персонажа, уже потерянного старой версией. Его имя остаётся занятым в `characters`. Перед обычным восстановлением/созданием Cardinal выполняется ограниченный read-only поиск потерянного владельца.

### Безопасные границы восстановления

`BotRosterRecovery` рассматривает только `Cardinal`/`Bishop`, `classid=97`, `base_class=97`, `online=0`, `deletetime=0`, положительный objectId, отсутствие объекта в `World` и отсутствие соответствующей записи `accounts.login`. Аккаунт должен точно совпадать с текущим `AccountPrefix` плюс шесть ASCII-цифр в диапазоне100000–999999 — форматом `BotSpawner.createBot`. Пустой prefix запрещён. В поставленной сборке создание такого бота сохраняет персонажа, но не создаёт login-аккаунт; пользовательские аккаунты с существующим `accounts.login` исключены, даже если имя похоже на fakeai.

Совпадение одного ника не даёт права загружать персонажа. Чужие/онлайн/удаляемые персонажи не присваиваются, не переименовываются и не удаляются. Нет SQL UPDATE/DELETE/миграций. Кандидат возвращается в регистрационные карты через `putIfAbsent`; затем используются прежние `loadBot` → `registerBot` и сохранение registry. Новые имена/суффиксы не добавляются. При обоих занятых чужих именах отказ остаётся безопасным.

Сменённый AccountPrefix, вручную созданный login-аккаунт бота, другая схема БД, некорректный персонаж или ошибка его загрузки требуют отдельной диагностики. При SQL-ошибке восстановление не ослабляет проверки и пишет stack trace. `spawnBot` также теперь пишет полный stack trace, а не только строку исключения.

## Ник противника: приватное сообщение при прибытии

`OlympiadOpponentNotice` подключается один раз из `BotManager.init` **до** выхода при выключенных ботах. Глобальный `ON_CREATURE_TELEPORTED` проверяет реального онлайн-игрока с клиентом и назначенным gameId. Данные противника берутся из текущей нативной олимпийской игры и её пары, не из ближайшего персонажа или текущей цели.

Сообщение через `Player.sendMessage`:

> Олимпиада: ваш противник — НИК.

- Отправка только участнику пары, не наблюдателю и не боту без клиента. Работает человек–бот и человек–человек; оба человека узнают имя своего противника.
- Нужны нативный режим Олимпиады, законченная телепортация обоих участников, одинаковые gameId/instanceId и фактическое нахождение обоих в пределах2000 от центра соответствующего стадиона. Возврат в обычный мир не считается прибытием.
- В поставленном JAR `portPlayersToArena` задаёт gameId раньше, но включает режим Олимпиады **после** `teleToLocation`. Поэтому раннее событие не отсекается только из-за ещё не установленного mode/teleport-флага: при неготовности отправки есть ограниченные повторы через250/1000/2000мс. Перед каждой реальной отправкой все строгие условия проверяются заново. Постоянного таймера нет.
- Существующий `olympiadPreStart` вызывает ту же проверку как резервную точку. Повторные события/таймеры/предстарт не дублируют сообщение в одной игре. Запоминается identity объекта нативной игры, а не номер стадиона: следующий бой на том же стадионе получает новое сообщение. Игроки/игры не удерживаются сильными ссылками после завершения.
- Не меняет цель, боевые разрешения, бафы, регистрацию, движение, `ExOlympiadUserInfo` или флаг `isOlympiadStart`. Имя не требует начала боя и не публикуется в общий чат. В тренировку этот обработчик не добавляется.

## Проверки

- `python3 tests/fakeplayersai/cardinal_recovery_opponent_notice_tests.py`: **691 проверка** production recovery-фильтров/JDBC и native Player-уведомлений; все custom/effect-скрипты компилируются против поставленных JAR. JDBC-прокси проверяют SELECT, параметры, освобождение ресурсов и все запрещённые категории; реального запроса в MySQL нет.
- `python3 tests/fakeplayersai/cardinal_spawn_dagger_pressure_tests.py`: **880 проверок**; точные production-тела `spawnAll`, `missingRosterPresets`, `saveRegistry`, создание актёров инертное. Проверены неполный18-пул, заполненный дублями19-пул без97, повторный запуск,0/disabled, ошибки/занятость имён, registry; настоящий `BotTactics.step` сохраняет dagger-pressure.
- Связанные регрессии прошли: имена/Prominence509; Cardinal parity6062; one-summon10554+3530; rear-approach3168; Escape Shackle377; Soul Cleanse714; Dominator server Victory2031. Предыдущие механики не переписывались.

Это локальные проверки кода, не подтверждение появления бота на живом сервере. Native listener dispatch, расписание повторов, подключение к production DB, сетевой клиент и end-to-end телепортация требуют smoke-проверки после установки.

## Установка и live smoke

1. Остановить GameServer. Сохранить текущие custom-скрипты, свой registry, ini и резервную копию БД.
2. Обновить **все три production Java-файла** из таблицы согласованно: BotManager, BotRosterRecovery, OlympiadOpponentNotice. Остальные изменения47–50 должны оставаться установленными. JAR/core-patches/XML/ini этим исправлением не меняются.
3. **Не заменять production `registry.properties` репозиторной копией**, не удалять строки персонажей ради освобождения ника. Полностью перезапустить GameServer; не hot reload.
4. Проверить наличие97 под именем Cardinal либо Bishop, покрытие всех19 профессий и появление его objectId в собственном registry. Повторный рестарт должен восстановить того же персонажа без нового суффикса.
5. При восстановлении потерянного бота искать `recovered Cardinal registry candidate`; успешный итог — прежнее `bot Cardinal (Cardinal) is in the world` либо `bot Bishop (Cardinal) is in the world`. При сбое нужны свежие `Cardinal orphan lookup failed`, `spawnBot(Cardinal) failed`, `roster incomplete`, `Static bot names`, `registry save failed` **вместе со stack trace**. Лог candidate сам по себе ещё не означает успешный вход в мир.
6. Пройти реальную Олимпиаду человек–бот и человек–человек: после прибытия, ещё до начала боя, личный чат содержит точный ник соперника один раз; следующий бой на том же стадионе показывает нового противника. Наблюдатель и возврат в город не получают такое сообщение; UI/target/combat gate прежние. Отдельно проверить уведомление при выключенных AI-ботах.

Откат: при остановленном сервере вернуть предыдущий согласованный Java-комплект из резервной копии. Новый код не мигрирует БД; уже сохранённый registry не затирать старым без проверки актуальных objectId.
