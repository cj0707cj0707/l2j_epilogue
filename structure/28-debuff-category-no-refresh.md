# 28. Дебафы: запрет замены и обновления таймера категории

> Дополнительная проверка: [29](29-tank-defense-rush-loop-and-entry-heal.md) и тесты подтверждают тот же общий путь для Armor Crush362 и Rush Impact793; Hammer Crush не был исключительным навыком.

## Правило

На всех целях (игроках, ботах, саммонах и NPC) активный длительный дебаф блокирует новое длительное наложение:

- того же навыка, независимо от источника, уровня и заточки;
- той же категории контроля: **стан, страх, рут, сон, запрет навыков, дизарм, паралич, замешательство, запрет автоатаки, предательство**;
- для прочих дебафов — того же ненулевого `AbnormalType` ядра, например Poison. `NONE` не является общей категорией для всех навыков.

Магический/физический рут объединены; магическая/физическая блокировка навыков также объединены в одну категорию. Запрет автоатаки — отдельная категория. Разные категории могут сосуществовать по обычным правилам ядра. Это НЕ общий иммунитет ко всем контролям и НЕ дополнительный иммунитет после окончания эффекта.

**Hammer Crush:** первый стан длится5с. Повторный Hammer Crush или другой стан не удаляет старый `BuffInfo`, не запускает его заново, не меняет начальный тик и длительность. Повторный удар по-прежнему может нанести урон: мгновенная часть навыка выполняется ядром до помещения длительного эффекта в список. После фактического окончания/снятия стана новое наложение снова возможно с обычной проверкой шанса/иммунитета.

Проверка сделана ДО `stopSkillEffects`, изменения `_stackedEffects` и `initializeEffects`. Отклонённый новый эффект не получает `onStart` И НЕ получает ложный `onExit`, поэтому не снимает чужой стан/страх/дизарм.

**Составной длительный эффект:** если один `BuffInfo` содержит несколько непрерывных компонентов и хотя бы одна категория конфликтует, весь новый непрерывный пакет отклоняется. Мгновенный урон остаётся. Компоненты не вырезаются по одному: это сохраняет целостность общего таймера и статов ядра. Положительные бафы и их стандартная замена не изменены.

## Почему нужен патч ядра

`libs/GameServer.jar` содержит общий `EffectList.add(BuffInfo)`, который прежде удалял/заменял уже действующий эффект. Одной правки AI, XML или `Stun.onStart` недостаточно: к этому моменту старый эффект уже мог быть снят.

Чтобы не публиковать непрозрачный новый бинарник и не пересобирать декомпилированное ядро целиком, исходный JAR в Git оставлен неизменным. Перед запуском сервера выполняется воспроизводимый точечный установщик на Java25:

- поддерживаемый исходный SHA-256: `8f27196ca9d74b82bbe9ad0d12d70da0196fa4e0d1bf23595267b724c79a23dd`;
- добавляет проверку перед оригинальным телом `EffectList.add` через служебные переходы, сохраняя инструкции исходных методов без декомпиляции;
- согласует вход/инициализацию и удаление/массовое снятие: **сначала монитор владельца Creature/Player, затем монитор EffectList**. Это сохраняет порядок обычных level-up/passive/stat-путей ядра и не создаёт инверсию Player↔EffectList. Не используется blanket `synchronized` на методе списка;
- компилирует `DebuffCategoryGuard` против установленного ядра;
- сохраняет и побайтно проверяет ВСЕ остальные записи JAR;
- создаёт локальный проверенный резерв `libs/GameServer.jar.pre-debuff-no-refresh-8f27196ca9d7`;
- подменяет JAR атомарно, без неатомарного fallback;
- повторный запуск проверяет маркер, исходник, классы и хеш всего содержимого JAR, не перепатчивает его;
- неизвестный JAR, изменённый патч, неправильный резерв или ошибка компиляции останавливают запуск. Несовместимое ядро автоматически не переписывается.

Установщик предназначен ТОЛЬКО для остановленного GameServer. Не запускать вручную при работающем сервере. Блокировка установщика защищает от двух одновременных установок, но не является детектором работающей JVM сервера.

## Установка

Актуальное исправление Windows-запуска и журнал ошибок: [документ30](30-debuff-installer-windows-startup.md). Защита категорий остаётся обязательной; запуск без неё не используется как обход ошибки.

1. Завершить тренировки/возвраты и остановить GameServer.
2. Обновить репозиторий целиком, включая новые `game/core-patches/` и изменённые загрузчики.
3. Требуется **Java25 JDK**, не урезанная JRE: установщик использует компилятор и стандартный Class-File API. Библиотеки сервера не скачиваются из интернета.
4. Запустить обычный `GameServer.vbs`, `GameServerWindow.vbs` или `GameServer.sh` → `GameServerTask.sh`. При первом старте установщик создаст резерв и патч; последующие старты только проверяют его.
5. Если сервер запускается ИНЫМ способом (панель, собственный BAT, прямой `java -jar`), сначала в каталоге `game` при остановленном сервере выполнить:

```bat
java --class-path "." core-patches/debuff-no-refresh/InstallDebuffGuard.java ../libs/GameServer.jar core-patches/debuff-no-refresh/DebuffCategoryGuard.java
```

Прямой запуск старого JAR в обход новых загрузчиков/установщика **не включает правило**. Успех установки помечается строкой `Installed debuff category guard v1` или `Debuff category guard v1 verified; already installed.`

## Проверки и ограничения

`python3 tests/fakeplayersai/debuff_no_refresh_tests.py` и полный `suite_tests.py` работают на отдельной копии настоящего ядра. Сравниваются исходная и пропатченная ветви; проверяются существующий `BuffInfo`, исходные начальные тики/длительность, повтор того же навыка, более сильная версия, другой источник/навык той же категории, разные категории,8 реальных обработчиков и800 конкурентных попыток. Дополнительно реальные мониторы Player/EffectList проверяются для наложения и снятия со stat-подобными callback-блокировками; намеренно обратный порядок воспроизводит deadlock и отвергается тестом. Без живой БД, сетевого клиента и настоящего отсчёта боя. Нужна игровая приёмка: стан5с→повтор через2с, Fear, Root, Sleep, Silence/PhysicalMute, Disarm; эффект заканчивается по первому таймеру и затем снова накладывается.

## Откат

Резерв Git: `backup/before-debuff-category-no-refresh-2026-10-15` → `fd78a41694cf30305ed1f274e752ca6c7c5fcdba`. Это не дамп БД.

При остановленном сервере вернуть предыдущие загрузчики/исходники из резерва И восстановить `libs/GameServer.jar` из проверенного локального `.pre-debuff-no-refresh-8f27196ca9d7`. Если вернуть только JAR, новые загрузчики снова установят патч; если вернуть только исходники, уже установленное ядро сохранит правило. БД этот патч не меняет.
