# Исправление установщика защиты и Windows-запуска

## Что исправлено

Старое окно «Debuff guard installation failed» не показывало настоящую причину. Сам скриншот не позволяет отличить неподходящую Java, блокировку файла, неизвестное ядро или права доступа.

В старой связке найден и воспроизведён отдельный дефект: загрузчик помещал **тот же `libs/GameServer.jar`, который предстоит заменить**, в application classpath установщика. `ClassFile.of()`/проверка classfile могли загружать классы ядра стандартным resolver, а `JavaCompiler.run()` не давал явного закрытия файлового менеджера. Дескриптор целевого JAR оставался открыт перед атомарной заменой. Linux допускает такую замену, Windows обычно запрещает её. Проверка на Linux воспроизводит открытый дескриптор перед заменой; это не тест настоящего запуска Windows.

Исправление:
- установка запускается **без `-cp ../libs/*`**; явный `--class-path "."` исключает также чужой `CLASSPATH` из окружения (он тоже способен удерживать целевой JAR ещё при source-launcher компиляции);
- иерархия классов разбирается из байтов закрываемого JAR, без загрузки серверных классов в application classloader;
- `StandardJavaFileManager` явно закрывается до замены;
- сохраняются проверка исходного SHA-256, owner→list порядок блокировок, проверка всего payload, резерв, атомарная замена и отказ для неизвестного/повреждённого ядра;
- уже проверенная установленная версия v1 принимается без переписывания;
- оба VBS используют каталог своего файла, корректно заключают Java-путь в кавычки, не зависят от наличия DOS-имени `Progra~1`;
- полный результат установщика сохраняется в `game/log/debuff-guard-install.log`. Ошибка показывает код, путь журнала и его конец вместо общего предположения о Java.

**Игровые классы и данные не менялись.** На копиях JAR тест сравнивает все runtime-классы/ресурсы старой и новой установки: они побайтно одинаковы. Исключение — служебный marker Properties с временем записи. Следовательно, это не отключение/откат no-refresh, AI, Rush, тренировок или защиты танков.

## Как обновить

1. Остановить GameServer. Не запускать установщик рядом с работающим сервером.
2. Обновить репозиторий **целиком**, включая новый `game/InstallDebuffGuard.cmd`, оба VBS и исходники `core-patches`. Не удалять/откатывать установленные боевые механики и не восстанавливать JAR автоматически.
3. Требуется JDK25. `JAVA_HOME` должен указывать на каталог JDK (допускается `bin`); если переменная отсутствует, используется `java` из PATH. Некорректный существующий JAVA_HOME не маскируется выбором другой Java.
4. Запустить прежний VBS. Для проверки без запуска сервера можно открыть CMD в `game` и выполнить `InstallDebuffGuard.cmd`.
5. При ошибке открыть **`game/log/debuff-guard-install.log`** и передать его текст. Журнал не содержит параметров подключения к БД: это вывод установщика/компилятора. Не обходить проверку прямым запуском неподтверждённого JAR.

Различать причины по журналу: `AccessDeniedException`/файл занят — остановить другую JVM/проверить права и защитное ПО; `Unsupported GameServer.jar SHA-256` — другое ядро, его нельзя автоматически патчить; `marker/hash mismatch` — изменённая установленная версия, требуется разбор её файлов; ошибка Class-File API/компилятора — проверить указанную в журнале Java/JDK. Эти случаи не исправляются отключением защиты.

## Проверки и ограничения

Тесты используют только временные копии настоящего `GameServer.jar`. Старый вариант воспроизводит удержание дескриптора, новый проходит проверку отсутствия открытого target-JAR и отсутствия загрузки `org.l2jmobius.*` в JVM установщика. Дополнительно проверяется окружение с `CLASSPATH`, указывающим на заменяемый JAR. Проверяются установленный старой версией v1, резерв и неизменность runtime-payload. Регрессионные тесты дебафов и весь suite сохраняются.

В среде проверки нет живого Windows GameServer, клиента или БД. Статические VBS/CMD-проверки и Linux-модель файловых дескрипторов не заменяют запуск на машине пользователя. Скриншот показывает только общий отказ, поэтому точная первоначальная причина на той машине не установлена без журнала.
